## 1. Technical Approach for Each Requirement

### HEAL-01: Autonomous Failure Detection and Recovery

**Requirement:** System can detect and recover from agent failures autonomously.

**Technical Approach:**
- Leverage existing `HealthReportingMixin` (src/heretek_swarm/actors/mixins/health_reporting.py) - already provides `record_error()`, `health_check()`, `get_health_status()`
- Extend `StewardAgent._monitor_loop()` (steward.py:395-403) which already calls `detect_heartbeat_failure()` every 5 seconds
- Wire `StewardAgent.initiate_failover()` (steward.py:413-424) to trigger actual recovery via `ActorSupervisor._attempt_restart()` (supervisor.py:337-394)
- Current gap: `_handle_agent_failure()` only logs + tracks failed agents; it doesn't trigger restart

**Key Implementation Points:**
1. Add recovery orchestration to `_handle_agent_failure()` - call supervisor restart with backoff
2. Add recovery success/failure tracking with retry limit (max_restarts already in supervisor)
3. Emit recovery events via NATS for observability
4. Health-based routing: `LoadBalancer.set_instance_health()` (scaling.py:611-616) can exclude unhealthy instances

**Existing Patterns:**
- `StewardAgent.detect_heartbeat_failure()` - identifies stale heartbeats (steward.py:385-393)
- `ActorSupervisor._attempt_restart()` - actual restart logic (supervisor.py:337-394)
- `HealthReportingMixin.record_error()` - error tracking with thresholds (health_reporting.py:28-51)
- Circuit breaker pattern in `gateway/external_api.py` for external API resilience

### HEAL-02: Auto-Scaling Based on Load

**Requirement:** System can auto-scale agent population based on load.

**Technical Approach:**
- Existing `AgentPoolManager` (scaling.py:155-509) already implements trigger-based scaling
- `AutonomousRuntime._calculate_system_load()` (autonomous_runtime.py:317-332) uses CPU+memory
- Missing: queue-depth and latency-based triggers (per ROADMAP requirements)
- Scale-down uses `_find_idle_agent()` - needs graceful drain + retire logic

**Key Implementation Points:**
1. Add queue depth monitoring to `ScalingConfig` - integrate with task queue metrics
2. Add latency-based trigger (p95 response time) - already in config as `response_time_p95_threshold_ms`
3. Implement graceful scale-down: drain connections before terminate (`AgentStatus.DRAINING`)
4. Wire `AutonomousRuntime._scaling_loop()` (or create if missing) to use `AgentPoolManager`

**Existing Patterns:**
- `ScalingConfig` dataclass (scaling.py:59-84) with CPU, memory, queue, response time thresholds
- `AgentPoolManager._scale_up()` / `_scale_down()` (scaling.py:422-509)
- `AutonomousRuntime._scale_up()` / `_scale_down()` (autonomous_runtime.py:334-388)
- Cooldown tracking via `_last_scale_up_time` / `_last_scale_down_time`

### HEAL-03: Self-Maintenance Without External Intervention

**Requirement:** System can self-maintain without external intervention.

**Technical Approach:**
- Log rotation: implement via scheduled task checking log file sizes
- Database maintenance: `StateRepository` (state/repository.py) already has `load_state()` / `_load_from_db()`
- Configuration drift detection: compare current config against baseline stored in state

**Key Implementation Points:**
1. Create `SelfMaintenanceScheduler` class - runs periodic maintenance tasks
2. Log rotation: check size, compress, prune old logs (>7 days)
3. DB maintenance: vacuum, analyze, prune orphaned records
4. Config drift: snapshot baseline, compare on interval, alert on drift

**Existing Patterns:**
- `SwarmMetricsCollector._update_health_score()` (observability/metrics.py:236-256) for health tracking
- `IntegrationManager.restart_integration()` (integrations/manager.py:503-532) for service restarts
- NATS scheduled messages via `_heartbeat_loop` patterns

### EMER-01: Measurable Collective Intelligence

**Requirement:** Collective demonstrates measurable intelligence exceeding individual agents.

**Technical Approach:**
- `CollectiveIntelligenceMetrics.calculate_siq()` (metrics.py:507-591) already computes Swarm Intelligence Quotient

**Key Implementation Points:**
1. Validate SIQ calculation outputs meet ≥0.6 threshold

**Existing Patterns:**

**Technical Approach:**

**Key Implementation Points:**

2. Add novelty scoring: compare against known solution patterns

**Existing Patterns:**

## 5. Common Pitfalls and How to Avoid Them

### Pitfall 1: Restart Storms
**Problem:** Failed agent restarts repeatedly, creating restart loop that consumes resources.

**Mitigation:**
- `ActorSupervisor.max_restarts` limit (supervisor.py:349) - terminates actor after max restarts
- Add exponential backoff: track consecutive failures, increase delay
- Circuit breaker: if restart fails N times, wait longer before retry

### Pitfall 2: Scale Thrashing
**Problem:** System oscillates between scale up and scale down due to unstable metrics.

**Mitigation:**
- Cooldown periods in `ScalingConfig` (scale_up_cooldown_seconds: 300, scale_down_cooldown_seconds: 600)
- Stabilization window (scale_up_stabilization_seconds: 60) - threshold must hold before scaling
- Use averaged metrics over window, not instant values

### Pitfall 3: False Positive Emergence Detection
**Problem:** Random agent behaviors correlated by chance, classified as emergence.

**Mitigation:**
- Statistical significance testing in `calculate_statistical_significance()` (emergent_detection_utils)
- Require minimum participating agents (config: min_participating_agents)
- Proven vs. Unproven classification - requires Core Triad validation
- Weight by validation rate in final score

### Pitfall 4: Health Check Overhead
**Problem:** Excessive health checks consume CPU, especially with many agents.

**Mitigation:**
- HealthReportingMixin already async and lightweight
- 5-second monitor interval (Steward._monitor_loop) is reasonable
- Skip checks for terminated actors (supervisor.py:304)

### Pitfall 5: Missing Novelty Baseline
**Problem:** System can't determine if solution is truly novel.

**Mitigation:**
- Build known solutions library over time
- Compare against historical successful patterns
- Novelty score = new pattern not in known library × confidence

## 6. Implementation Order

### Phase 1: Foundation (HEAL-01, HEAL-02的基础)

**Order:** HEAL-01 → HEAL-02

**Rationale:** Self-healing must work before auto-scaling can safely add/remove agents. Both depend on health infrastructure.

1. **HEAL-01.A:** Wire `_handle_agent_failure()` to call supervisor restart
2. **HEAL-01.B:** Add recovery event emission (NATS topic: `system.recovery`)
3. **HEAL-01.C:** Add restart cooldown / backoff
4. **HEAL-02.A:** Add queue depth trigger to ScalingConfig
5. **HEAL-02.B:** Add latency-based trigger
6. **HEAL-02.C:** Implement graceful drain for scale-down

### Phase 2: Self-Maintenance (HEAL-03)

**Order:** After HEAL-01/02

**Rationale:** Self-maintenance can be independent, but benefits from established health monitoring.

1. **HEAL-03.A:** Create SelfMaintenanceScheduler
2. **HEAL-03.B:** Add log rotation task
3. **HEAL-03.C:** Add DB maintenance task
4. **HEAL-03.D:** Add config drift detection

### Phase 3: Emergent Intelligence (EMER-01, EMER-02)

**Order:** EMER-01 → EMER-02

**Rationale:** EMER-01 provides measurement infrastructure that EMER-02 needs for validation.

1. **EMER-01.A:** Wire metrics collection to periodic interval
2. **EMER-01.B:** Add validation event tracking
3. **EMER-01.C:** Implement weighted scoring
4. **EMER-02.A:** Implement `analyze_for_emergence()` stub
5. **EMER-02.B:** Add novelty scoring against known patterns
6. **EMER-02.C:** Add Proven/Unproven classification

## 9. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|-------------|
| Restart storms consuming resources | Medium | High | Max restart limit + exponential backoff |
| Scale thrashing under unstable load | Medium | Medium | Cooldown periods + stabilization windows |
